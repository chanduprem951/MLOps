# Full notes: the 41-stage MLOps lifecycle

## Architecture and artifacts

Azure Repos commit -> CI data checks -> held-out split -> scaling plus logistic regression -> metrics and validation -> quality gate -> tested FastAPI -> scanned Docker image -> ACR digest and Azure ML registry version -> development -> staging -> approval -> production Container App. Production samples plus delayed labels -> drift report -> retraining pipeline -> the same release gates.

Training creates `data.csv`, `train.csv`, `test.csv`, `features.json`, `model.joblib`, `metrics.json`, `manifest.json`, and `baseline.csv`. The manifest associates Build ID, commit, training data SHA256, model SHA256 and evaluation metrics. Azure Pipeline artifacts preserve this evidence. ACR tags use the Build ID, but deployment resolves and uses the digest. Azure ML model versions also use the Build ID.

The following notes distinguish implemented code from Azure configuration that must be completed in the actual subscription.

## CI versus CD versus scheduled monitoring

CI provides evidence about source, dependencies, data, model and API before publication. CD promotes a single tested image through separate environments. Scheduled monitoring evaluates the currently deployed version and can request a new CI run. These are separate pipeline runs because monitoring must continue after a release finishes, and retraining is not needed on every release.

## Data and model limitations

The demo is intentionally small and deterministic. It has no hyperparameter sweep, feature store, streaming ingestion, production-label collection or fairness evaluation. Schema and class assumptions are specific to Iris. Replace them explicitly for your intended model. Keep dataset identifiers and immutable snapshots; never download changing training data under an unversioned name during a release. Monitor inputs should be de-identified according to the domain and retention policy.
